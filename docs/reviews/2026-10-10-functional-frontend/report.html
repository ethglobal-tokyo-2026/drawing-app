1 · P1 Preserve board save ordering across tab changes

apps/frontend/src/sticker-board/StickerBoard.tsx:401–418; board unmount: apps/frontend/src/app/App.tsx:235–244.

The placement queue belongs to a mounted Sticker Board. Leaving and returning creates a second queue while callbacks from the first continue sending. An older queued placement can reach the server after a newer move and permanently replace it.

Reproduction
Move a sticker left; delay that request; move it left again; leave and return to the board; move it right; release the original request. The previous visit sends its queued leftward move after the rightward move. A second reproduction shows a pending move disappearing from the screen and local cache when a stale board response is adopted on return.
Evidence
Focused regression assertions fail: the server ends at x=0.4402 instead of the latest x=0.5299; the simpler return loses x=0.4701 and shows x=0.5. See the verification output below.
Fix
Keep placement requests, pending placements, and failures in account-scoped state that survives board mounts. Apply pending placements over server reads until acknowledged. Preserve ordering across every visit, including Large layout edits.
Regression to retain
A delayed save and a queued move from an earlier visit cannot overwrite the latest move, and a stale read cannot erase a pending placement or its failure.

2 · P2 Associate saved strokes with their ticket

apps/frontend/src/sticker-creation/session/keptSession.ts:244–252,517–518.

Starting a session writes its new ticket into localStorage before clearing IndexedDB. The stored steps have no ticket identifier. If the clear fails, restoration combines the old steps with the new ticket.

Reproduction and evidence
Save a red stroke under ticket 7; make IndexedDB writes fail while reads remain available; start ticket 8; reload the session. The actual result is status: found, ticket 8, and ticket 7's red stroke. This can attach an old drawing to a newly spent ticket.
Fix
Store the ticket or session identity in the same IndexedDB transaction as its steps and validate that identity during restoration. A mismatched record must enter explicit recovery instead of being accepted as the current drawing.
Regression to retain
Failure or interruption of the reset between two tickets never restores the previous ticket's strokes as the new one's.

3 · P2 Preserve the recipient when recovering a gift

apps/frontend/src/giving/giftBackend.ts:226–238; related API behavior: apps/api/src/gifts/packaging.ts:172–174,195.

Gift recovery calls the mutating packaging endpoint before checking saved send state. When Giving is reopened from your own board, no recipient is supplied. The API interprets that as clearing the recipient of the already packed gift.

Reproduction and evidence
Start Giving from Bob's board; retain an uncertain LINE send outcome; reopen the sticker from your own board; confirm “It went out.” A reproduction using the actual API test app confirms that Bob's Gifts for you response is empty afterward. The original Gift Message can still carry a link, but Bob loses delivery through his board.
Fix
Separate resuming a packed gift from changing its recipient. Inspect saved send state before a recipient-changing request, and preserve the existing destination unless the giver explicitly changes it.
Regression to retain
A selected recipient survives uncertain-send and failed-report recovery from the giver's own board.

4 · P2 Preserve gift send state when device storage fails

apps/frontend/src/giving/keptGifts.ts:69–73; recovery reads: apps/frontend/src/giving/giftBackend.ts:229–250.

keepGift() discards the result of the storage write and keeps no in-memory fallback for “sent” or “maybe sent.” Gift Claim Tokens are retained separately in memory, so a failed marker write permits the same message to be offered again.

Reproduction and evidence
Make localStorage throw QuotaExceededError when the uncertain-send marker is saved, then reopen Giving on the same page. The backend returns the identical Gift Message and token for another send. After a reload, losing that marker also permits the recovery path to take the gift out without recognizing that its message may already have gone out.
Fix
Retain send state in memory and surface persistence failure to Giving. Protect reload recovery with durable server state or an explicit restriction when the app cannot safely retain the outcome. Logging alone does not preserve this invariant.
Regression to retain
Full or unavailable storage cannot reoffer a possibly sent token or silently authorize taking that gift out during recovery.

5 · P2 Recover the wallet provider after its error boundary trips

apps/frontend/src/identity/PrivySignIn.tsx:12–28,41–45; retry status change: apps/frontend/src/identity/privy.ts:87–93.

Once the wallet provider throws, PrivyBoundary permanently renders nothing. Retry resets the shared status to “signing in” but neither resets nor remounts that boundary. The wallet provider remains absent, so sealing, giving, receiving, and paid purchases cannot recover through the offered retry.

Reproduction and evidence
Make the provider fail once, allow it to succeed afterward, then invoke the app's retry and rerender. Status changes to “signing in,” but the provider's render count does not increase and the boundary still renders nothing.
Fix
Provide a real reset/remount path for a provider failure. For a failed module import cached by the browser or React, offer reload as the recovery action rather than a retry that changes only status.
Regression to retain
A transient provider failure followed by Retry either restores the wallet provider or explicitly offers the reload required to do so.

6 · P2 Stop captured strokes when drawing is paused

apps/frontend/src/sticker-creation/canvas/inkEngine.ts:228–233; clock holds: apps/frontend/src/sticker-creation/DrawingScreen.tsx:744–753.

The input settings terminate a live stroke only when locked changes. Changes to paused or panelOpen leave a captured stroke active, and later move events continue adding ink while the regular session's clock is stopped.

Reproduction and evidence
Hold the Pencil down, pause with a finger, then continue moving the Pencil. The engine reproduction pauses at x=30 and still commits the later endpoint at x=220. Opening a tool panel during that stroke has the same missing interruption.
Fix
End a live stroke and cancel a pending fill when settings transition into a state that prevents drawing. Require a new permitted pointer-down before accepting new ink.
Regression to retain
Pausing or opening a panel during a captured stroke preserves only the ink drawn before the hold.

7 · P2 Bound timelapse fill snapshot memory

apps/frontend/src/sticker-board/timelapse/fillSnapshots.ts:186–188.

Preparation retains a separate canvas for each changed fill until playback begins. A timeout bounds the duration of preparation, but there is no limit on the total retained pixels. Repeated fills produce compact recorded operations while their expanded snapshots can be large.

Reproduction and evidence
Using the existing test canvas implementation, 40 full-region fills retain 40 canvases and 1,600,000 RGBA bytes at only 100 × 100 pixels. The same allocation formula at 1000 × 1000 is 40 × 1000 × 1000 × 4 = 160,000,000 bytes, before working canvases and browser overhead. Allocation growth is demonstrated; a browser crash threshold was not measured.
Fix
Set a total snapshot-byte budget. Prepare only a bounded number of upcoming fills, or deliberately fall back when the budget is exceeded. Keep failure and cancellation cleanup.
Regression to retain
A replay with many large fills stays within its allocation budget and either plays or reports a controlled fallback.

8 · P2 Refresh checkout balance after funding the wallet

apps/frontend/src/tickets/ReserveTicketCheckout.tsx:110–132,533.

A successful balance read is not refreshed when the app resumes or when the wallet receives JPYC. The checkout tells someone with insufficient funds to add JPYC, but its Pay button stays disabled against the old balance until the checkout is closed and reopened.

Reproduction and evidence
Open checkout with a zero balance, then make the balance provider return enough JPYC. Dispatch visibility, focus, and online events and advance the clock. The provider is still called only once, the checkout still shows ¥0, and Pay remains disabled.
Fix
Refresh after returning to the app and provide an explicit balance refresh action, or use bounded polling while insufficient funds are shown. Keep the request timeout and avoid overlapping balance requests.
Regression to retain
Funding the wallet and returning to checkout updates the balance and enables an affordable pack without reopening the checkout.

9 · P2 Reconcile ticket counts when a read overtakes a spend

apps/frontend/src/tickets/TicketsProvider.tsx:110–114.

Request numbers prevent an older request's answer from replacing a newer one, but request-start order does not guarantee the order in which the server processed them. A ticket read started after a slow spend can return the pre-spend count. The eventual spend answer is discarded without the reconciliation already used for purchases.

Reproduction and evidence
Start a spend; refresh tickets while it is pending; let that read return three daily tickets; then resolve the spend with two. The provider continues showing three and issues no follow-up read. A refill or resume-triggered read can create this overlap.
Fix
If a completed spend's count cannot be adopted, refresh the authoritative ticket count, as the purchase paths already do. A server-provided revision would also allow reliable ordering.
Regression to retain
A read that overtakes a pending spend cannot leave the UI displaying a ticket that has already been consumed.

10 · P2 Handle Android and LINE Back in the Gratitude Mini-game

apps/frontend/src/gratitude/GratitudeMiniGame.tsx:292–299.

The game handles its close button, Escape, and receipt drag, but does not register with the app's Back stack. From sticker detail, the previous overlay entry is removed without a game entry taking its place. Android or LINE Back can leave the app instead of ending the combo and showing its receipt; a game opened over the stat board can instead affect that underlying board.

Reproduction and evidence
The rendered game creates no history entry and ignores a popstate event. Its parents and the shared Back implementation were checked to confirm that no other layer handles this game's transition.
Fix
Register the game with useBackToClose. Back during play should end the combo and retain an entry for the receipt; Back on the receipt should close it.
Regression to retain
Back before play closes, Back during play records once and shows the receipt, and Back from the receipt closes without leaving Croquis.

11 · P2 Keep Explore pages and position through phone searches

apps/frontend/src/explore/ExploreScreen.tsx:804; pagination state: apps/frontend/src/explore/pilePages.ts:65.

In one column, a search unmounts the pile and its pagination state. Clearing the search creates a fresh pile containing only the first page. Previously loaded older stickers disappear, the reading position is lost, and those pages must be fetched again. Switching to This week follows the same unmount path.

Reproduction and evidence
Load Today and an older day's page; search for an artist; clear the search. A focused regression assertion expects both days but receives only Today. Existing retention coverage exercises the two-column layout, which hides the pile instead.
Fix
Keep the pile's state through temporary search and leaderboard views, and retain its scroll position. Hidden work can be suspended without discarding loaded pages.
Regression to retain
Phone search/clear and pile/leaderboard switches preserve loaded pages and return to the previous reading position without duplicate page requests.

12 · P3 Wait for sticker-detail closing in the Escape test

apps/frontend/src/sticker-board/StickerDetail.test.tsx:111,1019–1020; close completion: apps/frontend/src/sticker-board/detailLift.ts:268–279.

The test waits one zero-delay timer tick before asserting that onClose ran. Closing intentionally waits for reversed animations to finish. Under scheduling contention, those animation timers can complete after the test's single tick and fail an otherwise correct close.

Reproduction and evidence
The full suite failed the Escape assertion after an earlier clean pass. The entire sticker-detail test file and repeated isolated runs passed. A controlled scheduling-delay reproduction confirmed that closing starts immediately, disables pointer interaction, and calls onClose once after the animation completes.
Fix
Wait for the observable close with vi.waitFor, or explicitly finish the animations using a deterministic test clock. Do not change application closing behavior to satisfy the premature assertion.
Regression to retain
The existing test verifies that another sticker's pending 18+ mark does not block closing, regardless of animation scheduling.

Scope and limits

Reviewed functional paths across app startup and navigation, API queries and session recovery, LINE and Privy integration, ticket spending and purchases, drawing input and saved sessions, Kyoto Seika Practice Mode, sealing, boards and Large layout, sticker detail and settings, Explore, giving and receiving, Gratitude and its replay/outbox, timelapse, shared hooks, and performance instrumentation. API handlers were traced where they determine frontend behavior. Existing tests were read alongside the implementation.

No live LINE picker, live wallet transaction, device sensor, physical Pencil, or device-memory measurement was performed. The full browser end-to-end suite was not run. The timelapse finding demonstrates allocation growth, not a measured crash threshold.

A delayed Gratitude outbox resend continues after its listener cleanup. A focused test reproduces that behavior and deletion following a 403, but a normal account-switch path without page teardown was not established. It is excluded from the confirmed fix list rather than presented as proven cross-account data loss.

Start with board-save persistence, saved-session identity, and gift-recovery state. Follow with wallet recovery, pause behavior, and the timelapse allocation budget; then close the checkout, ticket-count, Back-navigation, and Explore retention gaps.
