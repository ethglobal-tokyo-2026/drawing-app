# Internationalization: design

2026-09-26, against `main` at 638c7a9. Puts the technology for Japanese and English in place: the library, the language, the catalogs, fonts, formatters, API errors, the Gift Message and the chat menus. Translating is out of scope beyond the token strings below.

**Sources.** AGENTS.MD "Internationalization"; PRODUCT.md "Users" and "Accessibility & Inclusion"; DESIGN.md "Typography"; the LIFF, Messaging API and i18next references under "References".

## Decisions

1. **i18next with react-i18next** (ad0ll: the standard library, over Paraglide JS and Lingui).
   - The catalogs are `.ts` files. English is `as const`, so keys and `{{variables}}` are typed; imported JSON would lose those types.
   - Calls use the selector API, `t(($) => $.giving.openYourGift)`, which i18next plans as its only typed form.
   - Checked against TypeScript 7.0.2 with i18next 26.4.2: an unknown key and a misspelled variable fail typecheck. **A call that leaves out its variables entirely still compiles** and prints `{{name}}`, so review has to catch that one.
2. **One chat menu image per language** (ad0ll). LINE draws no text on a menu besides its chat bar label, so each language is its own menu, with its own image, chat bar text and area labels.
3. **The Gift Message is in the giver's language** (ad0ll). LINE's friend picker answers only `{ status: "success" }`, never who was picked, so the app can't know the recipient's language. Once the recipient opens the gift, the app is in their own language.
4. **The Japanese UI hides the pop-in words' English glosses** (ad0ll). The Japanese words stay in both languages. The tier names' glosses (`tierNames.ts`) follow the same rule.
5. **The terms and privacy pages aren't translated** (ad0ll).
6. **The language comes from LINE.**
   - `liff.getAppLanguage()` returns a BCP 47 tag and works before `liff.init()`.
   - In LIFF SDK 2.31 it asks LINE only on iOS inside LINE 14.11.0 or newer. Everywhere else it returns `navigator.language`.
   - LIFF Mock answers `"en"`. `liffMock.set((d) => ({ ...d, getAppLanguage: "ja" }))` in the console changes it.
   - A tag whose language subtag is `ja` maps to `ja`; anything else maps to `en`.
   - Unverified: whether Android's LINE browser reports LINE's language or the phone's.
7. **`users.language`** (ad0ll, 2026-09-26).
   - A `"ja" | "en"` column, sent at sign-in beside `timeZone` and refreshed at every sign-in, like the LINE name.
   - The server will then write the Official Account's later pushes in each person's language. That includes the edge case where a gift's recipient is already a user.
   - Nothing reads it in this work.
8. **A few obvious elements get real Japanese, enough to prove each path works** (ad0ll, 2026-09-26: "Do some basic translations of a few obvious elements to prove it works"):
   - the tab bar's labels (`TabBar.tsx`)
   - the LINE sign-in gate (`LineGate.tsx`)
   - the Gift Message's button and `altText` (`giving/giftMessage.ts`)
   - one refusal screen, "Already opened" (`receiving/refusals.ts`)
   - one API error message, `sticker_not_found` on the sticker detail
   - the chat menu's labels (Draw · My board · Explore) and its chat bar text

   The formatters need no translated strings: they follow the active language through `Intl`.

9. **Automatic Japanese stays off until `ja.ts` is complete** (ad0ll, 2026-09-26). Everyone sees English, and a language switch on the dev slip shows the Japanese. Turning automatic Japanese on is one line once `ja.ts` is typed as complete (see "Testing").

## Architecture

### Where it starts

- **The folder:** `src/i18n/`. It holds:
  - `en.ts`, `as const`
  - `ja.ts`, typed from `en`'s shape
  - `language.ts`, whose `languageOf(tag)` does the mapping
  - the i18next instance, and the `CustomTypeOptions` augmentation
- **Boot:** `main.tsx` starts i18n beside `initLine()`, before `createRoot().render()`. `liff.getAppLanguage()` doesn't wait for `liff.init()`, so the first screen, `LineGate`'s "Opening your sticker board…", is already in the right language. Both catalogs are bundled, so there's no fetch and no flash of English.
- **LIFF's own text:** `liff.i18n.setLang()` gets the same language, so LIFF's own text matches. It also works before `liff.init()`.
- **The dev slip's switch** stores its choice in `localStorage` and wins over LINE's language. `changeLanguage` re-renders everything.
- **Code outside React** calls the same instance's `t`. That covers `giftMessage.ts`, `refusals.ts`, and the Mini-game's screen-reader `say()` lines in `miniGameEngine.ts` and `gameEndings.ts`.

### The page's language

- `<html lang>` follows the active language on every change. It picks the Japanese glyph forms of kanji in fallback fonts, since Android's Noto CJK chooses by `lang`, and it sets screen readers' voices. `index.html` keeps `lang="en"` until the script runs.
- `document.title` ("Sticker Board") comes from the catalog.

### Fonts and line breaking

- **The UI stack:** `--font-ui` in `styles/tokens.css` adds Zen Kaku Gothic New after Mona Sans, DESIGN.md's Japanese face. Latin stays in Mona Sans and Japanese falls through to Zen Kaku, in both languages, since Japanese names like ゆず appear in the English UI too.
  - `index.html` already loads Zen Kaku Gothic New (500 and 700).
  - Dela Gothic One (`--font-puffy`) already has Japanese glyphs.
- **Line breaking:** `:lang(ja)` gets two rules.
  - `line-break: strict` keeps small kana and closing brackets off a line's start.
  - `word-break: auto-phrase` wraps at phrases where the browser supports it. iOS WebKit ignores it and wraps anywhere.
- **Longer strings:** layouts keep tolerating them (PRODUCT.md).

### Formatters

- **Formatters pinned to `en-US`** take the active language. They're in `TransferTrail.tsx`, `trailRows.ts`, `StatCork.tsx`, `ExploreScreen.tsx`, `OfferSheet.tsx`, `comboHud.ts`, `GratitudeMiniGame.tsx`, `gameEndings.ts`, `miniGameEngine.ts` and `tickets/refill.ts`. Numbers group the same way in both languages; times of day don't (4:52 PM, 16:52).
- **Hand-written plurals** (`n === 1 ? "ticket" : "tickets"`) become i18next plurals (`_one`, `_other`), chosen by `Intl.PluralRules`. Japanese has only `other`.
- **`formatDuration`'s units ("4m 52s") and `spokenDuration`** move to the catalog.
- **These stay as they are:**
  - `stickers/format.ts`'s printed forms (No.0147, 2026.09.23, 9.23), which are part of the design's look in both languages
  - yen prices (`prices.ts`, already `ja-JP`)
  - the API's `en-US` formatters (`ticketDays.ts`, the session route's time zone check), which only parse

### API errors

- **The server's side doesn't change.** It keeps answering `{ error, detail? }`. `error` is the contract; `detail` stays English, for logs and developers.
- **The app's side:**
  - The catalog has one message per code (`errors.<code>`).
  - A screen shows that message, with `detail` as fine print under it, so an error still says what failed (AGENTS.MD) without translating server text.
  - This replaces `reasonOf` in `StickerBoard.tsx` and `StickerDetail.tsx`'s `detail ?? code`.
  - A code the catalog lacks, and the client's own `network`, show a general message with the code.
- **The receive refusals** already switch on codes (`receiveFlow.ts` → `refusals.ts`). Only their text moves to the catalog.

### The Gift Message

- `buildGiftMessage` takes the giver's language as an input and builds every string from the catalog: `altText`, the number line, the tag, the body line and the button. It stays pure, with no global language, so the server can build the same gift message later.
- `giftTag`'s `label: "From" | "For"` becomes a catalog key, not English text. The GiftBag and the Gift Message print it through the catalog.

### Chat menus

- **Images:** `deploy/line/returning-menu.html` renders both images, `returning-menu.png` and `returning-menu.ja.png`.
- **The script:** `create-returning-menu.sh en|ja` makes one menu per run, with that language's image, `chatBarText` and area labels. Screen readers read the area labels.
- **Config:** `deploy/sticker-auth.env` gets `LINE_RETURNING_RICH_MENU_ID_EN` and `LINE_RETURNING_RICH_MENU_ID_JA`, in place of `LINE_RETURNING_RICH_MENU_ID`.
- **The switch:**
  - `requestReturningMenu` in `chatMenu.ts` adds `language` to its `POST /v1/auth/line-menu` body, and `auth-http.ts` reads it beside `idToken`.
  - `createLineMenuSwitch` links that language's menu; a missing or unknown language gets English.
  - Its "already linked" check compares against that language's menu. Since the switch runs on every page load, someone whose language changes gets the other menu the next time they open the app.
- **Moving everyone to a new menu ID:** LINE's `POST /v2/bot/richmenu/batch` `link` operation needs no user IDs.
- **The default menu,** for people who have never opened the app, can't know anyone's language: there's no webhook, so it's one menu for everyone. **Option:** a bilingual image. No script in `deploy/line/` makes the default menu today.

### Server-side language

- `users.language`'s column is `text("language").notNull()`, checked to `ja` or `en`. It defaults to `en` for existing rows.
- `signInBody` picks `language` beside `timeZone` through drizzle-zod.
- A returning sign-in refreshes it, the way it refreshes the LINE name.

### Not affected

- **Privy:** the JWT sign-in and the invisible wallet show no Privy screen. If one ever does, Privy 3.45's experimental `config.intl.textLocalization` takes its strings.
- **LINE's own screens** (consent, the friend picker, notifications): LINE translates them.

## Not in this work

- Translating beyond the token strings.
- **The LINE Developers Console's strings.** These are the LIFF app's name, the Login channel's consent screen, and the Official Account's greeting and auto-replies.
- The terms and privacy pages.
- The Official Account's pushes themselves.

## Testing

Tests that fail when the behavior breaks, and types where types can say it:

- **`languageOf`:** `ja` and `ja-JP` map to `ja`; `en-US`, `zh-TW`, `th` and an empty tag map to `en`.
- **The Japanese catalog's shape is a type,** so no test is needed.
  - `ja.ts` is typed as a deep partial of `en`'s shape, so a Japanese key that English lacks fails typecheck.
  - Turning automatic Japanese on tightens the type to every key.
- **Every API error code has a message.**
  - The catalog's `errors` is a record over the API's code union, so a new code without a message fails typecheck.
  - The union comes from the API's typed routes, where `apiError` keeps each code's literal type for Hono's client, not from a hand-written list.
- **The chat menu switch** (`line-menu` tests):
  - `ja` links the Japanese menu, and a missing or unknown language links English.
  - Someone already on the right menu isn't linked again.
- **`<html lang>`** follows `changeLanguage`.
