## How the chat menu works today (verified on main)

- `deploy/line/returning-menu.html` renders both images: `returning-menu.png` and, with `?lang=ja`, `returning-menu.ja.png`. `create-returning-menu.sh en|ja` makes one menu per run: 2500 × 843, three full-height columns (x 0, 833, 1666), `chatBarText` "Sticker Board" / "シールボード", links to `/draw`, `/` and `/explore` on the LIFF URL.
- `deploy/sticker-auth.env:12-14` sets only `LINE_RETURNING_RICH_MENU_ID_EN`, so Japanese would get the English menu (`packages/sticker-chain/src/start-auth-server.ts:15-56`). Suspected: the Japanese menu was never created in LINE. It doesn't matter yet: the app starts in English for everyone until the Japanese catalog is complete (`apps/frontend/src/i18n/language.ts:6-14`).
- The app calls `POST /v1/auth/line-menu` once per page load after the Privy sign-in (`apps/frontend/src/identity/PrivySession.tsx:47` → `apps/frontend/src/line/chatMenu.ts:47-79`). The sticker-auth server verifies the ID token, asks Privy whether the person has an account, links the language's menu and reads it back (`packages/sticker-chain/src/line-menu.ts:179-202`). Its own comment: "Privy's users stand in for accounts until the app has a users table" (`line-menu.ts:76-77`). The app has that table now.
- **The REST API already has what a per-person menu needs.** `users.lineUserId` is the raw LINE user ID (`packages/db/src/schema/users.ts:9-13`: "the Official account's push target"), set from the verified ID token at `POST /api/session` (`apps/api/src/routes/session.ts:71-106`), which the app calls on every load (`apps/frontend/src/api/SessionGate.tsx:51-55`). `users.language` is kept at sign-in too (`users.ts:38-41`). The sticker-auth server only keeps a hash (`privySubject`, `packages/sticker-chain/src/line-privy-jwt.ts:8-11`).
- Daily tickets turn over at midnight Tokyo time for everyone (`apps/api/src/ticketDays.ts:67-79`, used at `apps/api/src/tickets/tickets.ts:98,132`). The comment at `users.ts:25` ("Ticket days turn over at 4:00 here") is stale for tickets; 4:00 local is Explore's day.
- No webhook endpoint exists (repo search; also `docs/superpowers/specs/2026-09-26-i18n-design.md:121`). Every `/api` route but `POST /api/session` requires a session (`apps/api/src/app.ts:16,27`). The default "Open Sticker Board" menu for new people isn't made by any script (same spec line), and the greeting and auto-replies were left out of the i18n work as console settings (spec line 140).
- Deleting an account (`DELETE /api/me`, `session.ts:140-156`) doesn't unlink the returning menu (no LINE call there).

## Item 1: "3 a day" on the Draw tile

**Item:** "The '3 a day' thing … if you can show the user how many daily tickets they have left, that would be amazing. You could dynamically generate that, and then they would run out, come back … But if you don't have the ability … just remove the '3 a day' and have it be a Draw button."

**Now (verified):** The Draw tile carries a white pill, "3 A DAY" / "1日3枚", tilted -4° (`deploy/line/returning-menu.html`: the `.dot` rule and `<span class="dot" data-ja="1日3枚">`). Its comment gives the reason: "One image serves everyone, so the dot states the ticket rule rather than a count of what's left." Screenshots: `deploy/line/returning-menu.png`, `deploy/line/returning-menu.ja.png`, and "Today" in `/tmp/feedback-plan/line-oa/mock/sheet.png`. The app never states the rule. Every Draw key carries the counts left (DESIGN.md "Ticket counts"; `/tmp/feedback-plan/line-oa/board.png` shows "Draw ▮×3 ▯×0"), and the out-of-tickets card "doesn't restate the three-a-day rule" (DESIGN.md "Out of tickets"). The pill also isn't an app component: dot badges are coded-hue pills with Dela numerals, and a white tilted tag is the draw screen's PAUSED look.

**Cause (verified):** one image per language, linked to everyone, so it can't carry a count (F2, F11).

**Can it be dynamic? Yes: link a different menu per count.**

- States, following the tickets-model lane's rule ("show the tickets your next drawing can use", `/tmp/feedback-plan/tickets-model.md`): **3, 2 and 1 daily tickets left; reserve** (daily gone, reserve tickets held); **none**. 5 per language × 2 languages = **10 menus**, plus the 2 plain ones from step 1 below, far under the 1,000 cap (F1). Each redesign makes new ones (F2) at 100 creations an hour (F7): minutes of script time. The script should delete superseded menus once nobody is linked to them.
- On a spend or a purchase: `POST /api/tickets/spend` and `POST /api/ticket-purchases` (`apps/api/src/routes/tickets.ts:31-72`, `:85-136`) know the person. After either commits, the API links the menu for (language, state) with one call (F4, 2,000/s). It shows at once, even with the chat open under the LIFF app (F8).
- At midnight Tokyo time: one `POST /v2/bot/richmenu/batch` with 8 `link` operations (each language's 2, 1, reserve and none menus → its 3 menu) and `resumeRequestKey` = the new ticket day (F6). One call a day against a limit of 3 an hour, and no user list. On launch night, add plain → 3 for each language.
- On every app load: link the right menu. This replaces the sticker-auth route and heals any stale count.
- Each state's menu gets its own area label for screen readers (F3, ≤ 20 characters): "Draw, 2 tickets left" (20), "かく（のこり2枚）".

**What the server needs:**

1. Move chat-menu linking from the sticker-auth server into the REST API, behind `AppDeps` (`apps/api/src/deps.ts`), as a `lineChatMenu` service. Reuse `channelAccessToken`, `linkReturningMenu` and `hasReturningMenu` from `packages/sticker-chain/src/line-menu.ts:124-177`. The API gets `LINE_MESSAGING_CHANNEL_ID` and `LINE_MESSAGING_CHANNEL_SECRET` the way it already takes `PRIVY_APP_SECRET` from the auth server's `secrets.env` (`deploy/install-chain-env.mjs:17`, run from `deploy/deploy-api.sh:58,88`). Without them, or under dev sign-in (LIFF Mock's made-up user IDs would answer 400), the service is off and every call is a no-op, as sticker-auth's 503 `menu_switching_off` is today.
2. Menu IDs: a committed, non-secret map, for example `deploy/line/menus.json` (`{ "en": { "plain": "richmenu-…", "3": …, "2": …, "1": …, "reserve": …, "none": … }, "ja": { … } }`), filled by `create-returning-menu.sh en|ja plain|3|2|1|reserve|none`. It replaces `LINE_RETURNING_RICH_MENU_ID_EN/_JA`.
3. Link points:
   - `POST /api/line-menu` (session route, no ID token needed): replaces `/v1/auth/line-menu`; `chatMenu.ts` calls it after sign-in and keeps the developer slip's "Chat menu" row (`apps/frontend/src/line/LineDetails.tsx:31-46`) working. An API account is what makes someone returning, so the Privy lookup goes.
   - After a spend or a purchase commits: in the background, with any failure logged. Neither waits on LINE or fails because of it.
   - `DELETE /api/me`: unlink.
4. The midnight job: an in-process timer in the API set to `nextTokyoTicketDayStart(now)` (`ticketDays.ts:78`), plus a catch-up at boot when the day's batch hasn't run (keep the last run's ticket day in a small table). When LINE reports the batch done (F6), relink everyone who spent since midnight, from `ticket_uses` for the new day. **A spend made while the batch runs gets overwritten** to "3 left" whichever way LINE reads "linked before the request" (their 2-left menu is also a `from` menu), so this step is required.
5. Retire `/v1/auth/line-menu` in `packages/sticker-chain` once the API route ships.

**Failure modes:**

- Not a friend, blocked or deleted LINE: the link answers 200 and does nothing (F4); they see the default menu. When they add the account later, nothing relinks until their next app load, unless the follow webhook (item 3) relinks too.
- LINE slow or down at spend time: the count is stale until the next load or spend. A wrong count is a broken promise, so log every failed link and count them.
- Two spends close together: link the count read after the commit. The later link can carry the older count; the next load fixes it (suspected, rare).
- A spend while the chat is open: fine (F8).
- Cost: rich menu calls aren't messages (F15). One link per spend, purchase and load; one batch a day.

**Reserve tickets on the menu:** the reserve state shows the reserve ticket **without a count**, so the menu never says "used up" to someone who can still draw. Counts aren't recommended: they're unbounded, so they'd need buckets (1–9 and 9+: 9 more menus per language), a relink on every purchase and spend, and 18 more batch operations a night, to repeat a number the app shows one tap away. Once daily tickets are left, the menu shows only the daily ticket, even when reserve tickets are held.

**Fix:** build the live count, in two steps, so the menu is right even if step 2 slips.

- **Step 1, with item 2's redraw:** drop the pill and ship the plain Draw key (icon and "Draw" / "かく" only). Mock: `mock/A-coded-en-plain.png`.
- **Step 2:** render the five states with the tickets exactly as the app's Draw key shows them, and create the 10 menus and land the API work above.
  - If the tickets-model lane's proposal ships (tickets tucked behind the key's right end, `/tmp/feedback-plan/tickets-model/mock-A.png`): a Seal Yellow ticket "×N" for 3, 2 and 1; the Grape ticket with no count for reserve; the used backing for none. It fits the menu's left column (the key about 130px, the tickets about 45–60px, the column 202px).
  - If today's key stays: the Liner Lift chip after the label with the Seal Yellow ticket mark (`apps/frontend/src/tickets/ticketShape.ts`, 18 × 12) and "×N" in Figure type; at none, the empty mark and Ink Soft text (`apps/frontend/src/tickets/TicketCount.css:45-52`). Mocks of this version: `mock/A-coded-en-2.png`, `mock/A-coded-ja-3.png`, `mock/A-coded-ja-0.png`.

**Impeccable:** `/impeccable shape` settles what the none and reserve states show, then `/impeccable clarify` for the area labels in both languages. The API work is backend and outside impeccable.

**Size:** step 1: S. Step 2: L (the API service and its move from sticker-auth, the midnight job with its catch-up and fix-up, 10 images and menus, tests, deploy config).

**Decisions for ad0ll:**

1. Build the live count (recommended), or stop at the plain Draw key.
2. Reserve tickets: the reserve ticket with no count once daily tickets are gone (recommended), counts in buckets, or daily tickets only.
3. The none state: the app's own look at none. Under the tickets-model proposal that's the used backing printed with the refill time. One image serves every time zone, so the menu would print Tokyo's midnight ("0:00" / "12:00 AM"). Recommended: print it; the account's people are in Japan, and so is the hackathon (the repository's GitHub org is ethglobal-tokyo-2026). The alternative is the backing with no time.

**Overlaps:** item 2 (same image; build them together). The tickets-model lane owns how the Draw key shows tickets (inside the key today, behind it in its proposal) and the reserve rule; the menu copies whatever ships, and its batch changes with any change to the day's turnover. The tickets-motion lane: no effect (a menu can't animate). The icons lane: the key's Draw icon (the ticket mark isn't an icon).

## Item 3: the greeting when someone adds the account

**Item:** "The message that you get from the official account when you open it up doesn't really do anything for us. It just says, like, nice to meet you … It would be better to give the user something shorter or more descriptive or just better."

**Now:** set outside the code. No webhook exists, so the greeting comes from the Greeting message setting in LINE Official Account Manager (F12), which the i18n work left alone (spec line 140). ad0ll's paraphrase matches LINE's stock template ("{Nickname}さん、はじめまして！{AccountName}です。…" and its English version), so the account most likely still has the default (suspected; the Manager can't be checked from here). Auto-reply messages are on by default too (F12), so a person who types in the chat probably gets LINE's stock auto-reply (suspected).

**Cause (suspected):** LINE's default greeting was never replaced.

**Fix:** replace the text in LINE Official Account Manager now (no code, no deploy), and add a follow webhook only if item 1's step 2 lands. Each proposal says what the app is, what you do and where to tap, in the app's words (sticker, sticker board, draw, give; the Japanese catalog's シールボード, かく and ひらく):

- **A, shortest:**
  - EN: "Draw for five minutes, and your drawing becomes a sticker to keep on your board or give to a friend. Open Sticker Board from the menu below."
  - JA: "5分でかいた絵が、シールになります。ボードにはるのも、友だちにあげるのも自由。下のメニューからシールボードをひらいてください。"
- **B, with the name:**
  - EN: "Hi {Nickname}! On Sticker Board, every five-minute drawing becomes a sticker. Keep it on your board or give it to a friend. Tap the menu below to start."
  - JA: "{Nickname}さん、ようこそ！シールボードでは、5分でかいた絵がシールになります。ボードにはったり、友だちにあげたり。下のメニューからはじめましょう。"
